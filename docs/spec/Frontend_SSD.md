# TaapSaathi Frontend Software Design Specification

**Audience:** Frontend developer and integration tester  
**Status:** Final implementation specification  
**Governing document:** `PRD.md`  
**Primary objective:** Make the AWS intervention understandable, actionable, and reliable on a supervisor laptop and a rider's phone.

## 1. Scope and ownership

The frontend owner is responsible for:

- the supervisor operations dashboard;
- the rider mobile intervention screen;
- map and route presentation;
- Hindi and English content presentation;
- Polly audio playback;
- deterministic demo controls;
- polling and reconciliation with backend state;
- accessible loading, empty, success, and failure states;
- deployment through Amplify Hosting;
- final screen recording and visual QA.

The frontend does not calculate risk, select the new assignee, invent workflow state, generate routes, or contain Step Functions task tokens.

## 2. Technology decisions

| Concern | Decision |
| --- | --- |
| Framework | Next.js 16 App Router with TypeScript |
| Styling | Tailwind CSS with a small token file; no external component theme required |
| Data fetching | Native `fetch` through typed API-client functions |
| Server-state refresh | Two-second polling during active demo workflows; five-second polling otherwise |
| Local UI state | React state and reducer; no Redux |
| Maps | MapLibre GL JS displaying backend-provided GeoJSON; route generated by Amazon Location |
| Validation | Shared Zod or JSON Schema contracts from `packages/contracts` |
| Unit tests | Vitest and React Testing Library |
| End-to-end test | Playwright golden path |
| Hosting | AWS Amplify Hosting |

The application is intentionally small. Do not introduce a charting library, animation framework, global state library, or design-system package during the MVP.

## 4. Routes

### 4.1 `/`

Redirect to `/ops` in demo mode. Do not spend time on a marketing landing page.

### 4.2 `/ops`

Primary supervisor surface.

Required regions:

1. Header containing TaapSaathi, current hub, backend health, and last refresh.
2. Status summary for safe, caution, intervention, and awaiting supervisor.
3. Rider list containing Ravi, Asha, and Imran.
4. Map showing riders, three rest points, and the active route.
5. Selected-rider panel with environmental inputs and matched rule.
6. Active-intervention panel with response timer and current workflow state.
7. Reassignment result.
8. Audit timeline.
9. Collapsible demo controls with reset and heat-spike actions.

### 4.3 `/worker/[workerId]`

Mobile-first rider surface.

Required regions:

1. Language toggle.
2. Current status label and icon.
3. One short instruction.
4. Route summary when an intervention is active.
5. Audio replay.
6. **Take break** primary action.
7. **I feel unwell** urgent action.
8. Visible 112 emergency action with a disclaimer that TaapSaathi has not placed the call.

### 4.4 Demo controls

Demo controls may live in `/ops` or `/demo`, but only one implementation should exist.

Controls:

- `Reset demo`
- `Trigger simulated heat spike`
- optional `Trigger symptom branch` only if it invokes the same worker response API

The interface must label the environmental trigger as **Simulated for demonstration**.

## 5. Visual system

### 5.1 State tokens

| State | Color role | Icon | Required label |
| --- | --- | --- | --- |
| `SAFE` | green | shield-check | Safe |
| `CAUTION` | amber | sun | Caution |
| `HIGH` | orange/red | heat-wave or warning | Break recommended |
| `CRITICAL` | red | alert-triangle | Help required |
| `RESTING` | blue | cup or pause | Resting |
| `AWAITING_SUPERVISOR` | violet | phone | Awaiting supervisor |

Color alone must never communicate status. Every instance uses an icon and text label.

### 5.2 Responsive behavior

- Supervisor target: 1366 by 768 and 1440 by 900.
- Rider target: 360 by 800 and 390 by 844.
- At widths below 960 pixels, the operations map and panels stack vertically.
- The rider page has no horizontal scroll.
- Action buttons are at least 48 pixels high and remain within thumb reach.

### 5.3 Typography and density

- Use one sans-serif family already available through Next.js.
- Rider instructions must be at least 18 pixels.
- Avoid dense tables on mobile.
- The supervisor screen may use compact cards but must remain readable in a screen recording.

## 6. Localization

Use a small static translation dictionary. Do not introduce a full localization framework.

```ts
type Language = "en" | "hi";

type TranslationKey =
  | "status.safe"
  | "status.breakRecommended"
  | "action.takeBreak"
  | "action.feelUnwell"
  | "action.replayAudio"
  | "route.distance"
  | "route.restPoint"
  | "emergency.disclaimer";
```

Language preference is stored in `localStorage` and sent with worker-response requests when useful. Polly audio URLs are supplied by the backend; the frontend does not synthesize speech.

Essential Hindi copy must be reviewed by a native speaker or teammate before recording. Avoid machine-translated long paragraphs.

## 7. Shared types

The frontend imports types from `packages/contracts`. It must not create independent versions of API entities.

Core types:

```ts
type RiskState =
  | "SAFE"
  | "CAUTION"
  | "HIGH"
  | "CRITICAL"
  | "RESTING"
  | "AWAITING_SUPERVISOR";

type WorkerAction = "TAKE_BREAK" | "FEEL_UNWELL";
type SupervisorAction = "SUPERVISOR_ACK";

interface RouteView {
  distanceMeters: number;
  durationSeconds: number;
  restPointName: string;
  geometry: GeoJSON.LineString;
}

interface WorkerView {
  workerId: string;
  name: string;
  language: "en" | "hi";
  state: RiskState;
  instruction: string;
  interventionId?: string;
  route?: RouteView;
  audioUrl?: string;
  updatedAt: string;
}
```

The exact exported schemas in the repository are authoritative. This document defines intent, not a second source of truth.

## 8. API-client behavior

All calls go through `lib/api.ts`.

```ts
interface ApiResult<T> {
  data?: T;
  error?: {
    code: string;
    message: string;
    requestId?: string;
  };
}
```

Rules:

- Set a client timeout for every request.
- Validate successful responses with the shared schema.
- Show backend error messages in a controlled error banner.
- Never replace a failed backend operation with fabricated success.
- Disable action buttons while a response is pending.
- Include the request id in developer-only diagnostics.
- Retry `GET` polling failures with bounded backoff.
- Do not automatically retry `POST` actions unless the idempotency key is preserved.

## 9. Polling and state reconciliation

The frontend uses polling because it is reliable and sufficient for a 150-second demo.

### Operations dashboard

- Poll `GET /dashboard` every five seconds while idle.
- Poll every two seconds when an intervention is active.
- Use `GET /events?after={cursor}` for incremental timeline updates if implemented.
- Stop polling when the tab is hidden for more than 30 seconds; refresh immediately on visibility return.

### Rider page

- Poll `GET /workers/{workerId}` every two seconds during an active intervention.
- Poll every five seconds while safe.
- After a worker action, show `Submitting...` and reconcile with the next server response.
- Backend state always wins over optimistic state.

## 10. Map behavior

The backend returns:

- current worker coordinates;
- rest-point coordinates;
- Amazon Location route geometry;
- distance and duration.

The frontend renders these values with MapLibre. It does not calculate the route locally.

Required layers:

1. rider markers;
2. rest-point markers;
3. active route line;
4. selected-worker emphasis.

Keep mandatory map attribution visible. If the map tile provider fails, preserve the rider list, route distance, destination name, and workflow actions. The map is not allowed to block the intervention.

## 11. Component states

Each asynchronous component implements:

- loading;
- ready;
- empty;
- recoverable error;
- stale data;
- action pending;
- action rejected;
- completed.

Do not use full-page spinners after initial load. Preserve the last good server state and show a stale-data warning during polling failures.

## 12. Golden-path screen states

| Step | Operations dashboard | Rider page |
| --- | --- | --- |
| Reset | Three riders safe; Ravi owns task `delivery-001` | Safe status |
| Heat event | Ravi changes to high risk; workflow begins | Break recommendation appears |
| Guidance ready | Route and audio available | Route summary and audio replay enabled |
| Break accepted | Ravi shows resting | Confirmation and rest-point guidance |
| Reassignment complete | Asha owns `delivery-001` | No delivery-management detail required |
| Symptom branch | Urgent action appears | Help-request confirmation |
| Supervisor acknowledges | Timeline records response | Supervisor responding message |

## 13. Frontend test requirements

At minimum:

- render all risk states;
- verify language switching;
- verify action buttons call the correct endpoint once;
- verify action buttons disable while pending;
- verify API failure remains visible and does not fake success;
- verify polling updates a worker state;
- verify route geometry renders from fixture data;
- verify the 360 by 800 rider viewport;
- run one Playwright golden-path test against the deployed API or a contract-compatible local environment.

Full cases are defined in `test.md`.

## 15. Frontend stop conditions

Do not build:

- analytics charts;
- dark-mode variants;
- animated heat maps;
- 3D maps;
- custom illustrations;
- a marketing landing page;
- a chatbot;
- complex authentication UI;
- WebSockets;
- additional personas.

If the backend golden path is not working, frontend effort is limited to integration fixes, error handling, accessibility, and the two P0 screens.

## 16. Frontend definition of done

- `/ops` and `/worker/ravi-001` work on the deployed URL.
- The interface consumes shared contracts without local duplicate types.
- The heat-spike-to-break flow can be completed without a page reload.
- Hindi text and audio work.
- Every status uses text and icon as well as color.
- A failed API call is visible and recoverable.
- The rider page passes manual 360 by 800 inspection.
- The complete demo remains understandable with audio muted.
- The complete demo remains usable if map tiles fail.
- No unfinished navigation, button, or placeholder appears in the recording.
